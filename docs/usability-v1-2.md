## Scope and design decision

Read the maintained governance, personnel, directorate, OIO and operating documentation, examples, templates, proposals, readiness record and publication/validation tooling before editing. Baseline checks passed: 28 Markdown files, 346 relative links/fragments, 22 output routes and 1,319 local output links/assets/fragments. Baseline browser inspection showed six expanded sidebar groups and 20 displayed document links on the landing page, including deep reference documents before ordinary task instructions.

Most routine work already had a decision owner and did **not** require executive approval. v1.1 also already proposed one action/exception register, conditional executive layers and short/full case routes. Removing those safeguards or claiming their introduction again would be misleading. v1.2 therefore adds three substantial reading aids, groups concise role profiles beside existing mandates, and changes the landing/sidebar order. No major structural change or new governance amendment is justified by this scope.

The [staff guide](start-here/staff-guide.md) answers role/authority questions; [everyday tasks](operations/everyday-work.md) explains 16 common routes; [reporting help](oversight/get-help.md) separates a reporter's job from a case officer's manual. Their links lead to controlling policy. Existing forms remain valid; the reading guides are not new compulsory forms.

## Measurement method and limits

- **D:** substantive decisions/assessment outcomes in the stated scenario. Choosing an already-authorized moderation action is a decision, not another person's approval.
- **P:** fresh authorizations from another authority needed for the modeled action. P&C process verification, notification, record entry and technical execution are identified separately. Two required signatories are counted as two approvals even if obtained in one exchange. Qualification assessment is counted as D, not disguised as a managerial approval.
- **H:** responsibility transfers in the specific modeled role path after a staff request begins; table paths show them. They are not universal minimum staffing/handoff requirements. A person may hold compatible roles; this can reduce physical handoffs equally in either version. Referrals outside the modeled normal path add work in either version.
- **R:** functional participants in the listed path, including the initiating candidate/staff member where applicable. This is not extra organizational headcount; ordinary player recipients are excluded.
- **Reference footprint:** distinct maintained Markdown sources whose rules are represented by the task explanation. It is **not** a claim v1.1 forced every staff member to read every page. The new guide provides a one-page normal-route explanation; consequential exceptions still require canonical policy. Actual assignment records and local playbooks remain additional, unchanged dependencies.
- Counts describe documented/fictional paths, not observed elapsed time, successful adoption, retention, comprehension rates or guaranteed service. Shortest possible search paths can already be one page in v1.1. Reading instructions more easily does not eliminate an approval.

## Publication review

All 23 allowlisted sources contain generic public guidance/specifications, not real case files, private identities, tokens, recovery codes, custodian addresses or private storage locations. Due-process rules and blank templates are transparent policy material, not confidential investigation evidence. Generic security limits/recovery responsibilities are retained; **working** recovery information must not be added here.

| Source class | Build treatment | Safety limitation |
|---|---|---|
| Landing and three guides | Public, searchable; status/authority links visible | No actual intake channel or person's manager invented |
| Existing governance/personnel/directorate/operations/OIO sources | Public, searchable; canonical Markdown retained | No real restricted records; qualified case officers still need formal mandates |
| Proposals/review register, v1.1 readiness, v1.2 walkthroughs, migration/source map | Repository-only; no staged Markdown route or search entry | GitHub repository visibility may still make these public. This is not confidential storage |
| Completed cases/personnel data, credentials and working recovery inventories | Not present; prohibited in either source/build | Requires authorized restricted systems and tests, still unverified |

Publication and navigation are now separate explicit lists. Adding a sidebar item cannot silently stage a confidential file. Validation requires one sidebar entry per published source, rejects proposed/repository-only sources in the public list and checks exact staging contents as well as output routes.

## Research and design basis

Retrieved 2026-11-02: [GOV.UK identifying user needs](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs/) supports organizing content around things people need to do; [Home Office documentation guidance](https://engineering.homeoffice.gov.uk/patterns/write-effective-documentation/) distinguishes task/concept/reference information; [Starlight sidebar documentation](https://starlight.astro.build/guides/sidebar/) supports explicit slug links, manual groups and collapsed reference sections. Context7 checked current official Starlight configuration; existing framework versions remain unchanged.

These sources support design choices, not measured effectiveness of this community. The ordinary task role maps come from repository rules, not corporate benchmarks. No new policy scoring system, management platform, committee, mandatory training certificate or meeting is introduced.
